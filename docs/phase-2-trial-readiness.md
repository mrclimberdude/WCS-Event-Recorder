# Phase 2 offline acceptance and next room-recording trial

The implemented Phase 2 software provides scoped reviewed identity/schedule revisions, bounded PCM preparation and consolidated history. Real acoustic acceptance is pending a longer room-microphone recording. No paid recognition requests were made to implement or verify these features.

Use the [operator walkthrough](operator-guide.md) for the recording-to-review sequence and the [status page](status.md) for current capabilities and remaining gates.

## Available offline checks

Use the installed environment. Each output directory must be new; failed artifacts remain available for inspection. The acceptance runner blocks socket/DNS and real HTTP transport, uses synthetic PCM and declared/mocked observations, and never needs a token.

```powershell
.\.venv\Scripts\python.exe scripts/verify_phase2.py acceptance --output data/my-phase2-acceptance
```

The walkthrough exercises the installed CLI for PCM preparation, fixture processing, explicit identity/schedule plans and separate analyses, history, comparison with/without a saved report, diagnosis, export and independent evaluation. API-generated hash-bound synthetic evidence allows positive scoring without fabricating a hash on older fixture runs. A fixture run lacking a persisted source hash must still refuse evaluation. Additional actual-API checks cover saved partial prefixes, mocked missing continuation and checkpoint-owned revisions. Original exports, labels, captured statuses and checkpoint bytes stay unchanged.

The script writes provenance and a final result only after the selected checks complete. A failed or interrupted directory is not acceptance. Inspect outcome fields and retained error records. Default developer controls bound generated bytes, free space, wall time and cases; `--limits PATH` uses the [storage benchmark limits contract](benchmarks.md#release-c-storage-probes). They do not establish real event capacity.

Run resource probes separately with other heavy verification stopped:

```powershell
.\.venv\Scripts\python.exe scripts/verify_phase2.py resources --output data/my-phase2-resources --resource-grids 29 100
```

Resource probes separate synthetic setup from preparation, revision planning/analysis and history operations, and keep ordinary timing separate from allocation tracing. Preserve the individual samples, geometry, semantic controls and measurement limitations in the results. They are developer checks, not service-latency, acoustic or full-event guarantees.

## Prepare the forthcoming recording

1. Retain a single room recording and its event/room, format, recording-time anchor and timezone. Note microphone/device, placement, levels and audible interference. Keep source audio and private notes under ignored `data/`.
2. Prepare independently known song identities/version distinctions and approximate boundaries, including uncertain transitions, speech and unknown spans. The [label schema](evaluation.md#prepare-independent-labels) binds labels to exact source identity, hash, format and frames. Record actual session/DJ changes separately with timestamp uncertainty; the evaluator does not score those as ground truth automatically.
3. Use [PCM preparation](audio-preparation.md) for exact WAV trims or channel extraction. It retains a distinct derived source ID and rational mapping/anchor residual. Prepare labels for the exact chosen output; labels from an original recording do not automatically match a trimmed source. Compressed/container conversion, resampling and denoising are outside this preparation contract.
4. Declare the trial duration, recognition request ceiling, source/prepared-audio storage, retained database/checkpoints/workspaces, free headroom, latency and memory requirements. Review `plan-audd` before explicitly authorizing any paid execution. There is no standing paid-request allowance from this implementation task.
5. Process and inspect the saved evidence, recover eligible failures as needed, then use [scoped revisions](revisions.md) for reviewed identity and expected schedule changes. Do collection/reconstruction before review when further uploads are needed: legacy recovery operations refuse reviewed parents rather than discard the review. New observations require new explicitly targeted review inputs.
6. Compare original/recovered/revised analyses, inspect their [history](history.md), and evaluate unchanged independent labels. Raw candidate accuracy remains separate from reviewed analysis identity/grouping/timing. Reused outcomes and human correction do not count as independent recognition trials.

Use the detailed [room-recording acceptance guidance](evaluation.md#room-recording-acceptance) for representative noise, announcements, applause, repeated songs and boundaries. Preserve poor outcomes and uncertainty. Choose acceptance thresholds before interpreting the results rather than changing labels or policies to make a run pass.

## Gates that remain open

- Representative room-microphone recognition quality and longer acoustic accuracy.
- Actual activity/DJ attribution measured against independent event observations, rather than published schedule agreement.
- A longer recording's preparation, storage, latency and memory envelope on the intended machine.
- The separately opt-in real selected-error/missing recognition trials and their paid-request limits.
- Independent live recording, power/interruption resilience and deployment requirements in Phase 6. File replay and database checkpoint tests do not establish capture resilience.

Direct booth feeds, dual-feed alignment/selection and cross-feed comparisons remain optional deferred work. Initial room trials require no booth connection. Completed historical implementation plans, their verification records and earlier private labels remain preserved.
